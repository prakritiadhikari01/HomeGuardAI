# HomeGuardAI

**The real-time perception service of HomeGuard: An Intelligent Home Surveillance System.**

HomeGuardAI is a stateless FastAPI service that processes camera streams, detects and tracks people, recognizes household members by face, and reports structured detection events to the HomeGuard backend. It also hosts the locally run language-model features (event summarization and a conversational assistant). It performs perception only: identity, permissions, alert decisions, and persistent storage all belong to the backend.

> Companion repository: [**HomeGuard**](https://github.com/prakritiadhikari01/Home_Guard) (Django backend). HomeGuardAI cannot run a full deployment on its own, since it obtains cameras, enrolled faces, and event context from the backend.

---

## 1. Key Features

- **Human detection**: YOLOv8 (nano variant by default) restricted to people.
- **Multi-object tracking**: ByteTrack assigns a persistent ID to each person, so one visit is treated as one session rather than a stream of disconnected detections.
- **Face recognition**: InsightFace embeddings compared by cosine similarity against faces enrolled for the camera's own home only. A face enrolled in one household can never match in another.
- **Motion gating**: OpenCV MOG2 background subtraction avoids running heavy models on static scenes.
- **Event reporting**: sessions are opened, updated, and closed on the backend as the tracked person appears, remains, and leaves.
- **Automatic enrichment**: on session close, a clip and thumbnail are produced and a one-sentence description is generated by a vision-language model (Qwen2.5-VL via Ollama), with a rule-based fallback.
- **Conversational assistant**: answers natural-language questions about a home's recent events using a local text model (gemma3:4b via Ollama), strictly from event data supplied by the backend.
- **Door verification**: a one-shot capture-and-match endpoint, called by the backend only when a member explicitly requests an unlock. It is independent of the continuous detection pipeline.
- **Dynamic camera management**: active cameras and their settings are synchronized from the backend periodically, so cameras can be added, changed, or removed without restarting the engine.

## 2. Design Principles

| Principle | How it is applied |
|---|---|
| Separation of concerns | The engine perceives; the backend decides. Alerts are raised by the backend, never here. |
| Stateless engine | No database, no local persistence of faces or media. Face embeddings are fetched from the backend per home; clips and thumbnails are uploaded to the backend and cloud storage. |
| Household isolation | Face matching is scoped to the home that owns the camera. |
| Local AI | Language models run on-premises through Ollama; no external inference API is required. |
| Fail-safe behavior | Backend communication failures are caught and returned as error results; summaries fall back to a rule-based description if the vision-language model is unavailable. |

```
                        │  detect · track        │  users · homes · roles

                        │                        │
                     Ollama (local LLMs)      Cloudinary (media)
```

## 4. Processing Pipeline

Each active camera is handled by an independent worker:

1. **Frame capture** from the camera stream registered in the backend.
2. **Motion gate** (MOG2): skip frames with insufficient motion.
3. **Human detection** (YOLOv8).
4. **Tracking** (ByteTrack): persistent track ID per person.
5. **Recognition** (InsightFace): classify the track as a known member or unknown, using the home's enrolled faces.
6. **Session reporting**: open on first resolved sighting, send progress updates while the track is active, close when the track is lost.
7. **Enrichment**: build a clip (with pre-/post-event buffer) and thumbnail, upload them, generate a summary, and attach everything to the closed event.

## 5. Backend Integration

HomeGuardAI communicates with the backend over HTTPS/HTTP, authenticated with a shared secret. Calls made by the engine:

| Purpose | Method and path (under `DJANGO_API_URL`) |
|---|---|
| Open a detection event | `POST /events/open/` |
| Update an open event | `PATCH /events/<id>/progress/` |
| Close an event | `PATCH /events/<id>/close/` |
| Attach clip, thumbnail, summary | `PATCH /events/<id>/enrich/` |
| Upload clip file | `PATCH /events/<id>/upload-clip/` |
| Upload thumbnail file | `PATCH /events/<id>/upload-thumbnail/` |
| Fetch active cameras | `GET /devices/active/` |
| Fetch a home's enrolled faces | `GET /homes/<home_id>/faces/` |
| Fetch recent events for the assistant | `GET /homes/<home_id>/events/context/` |
| Submit a completed face enrollment | `POST /enrollment/complete/` |

Ordering rule: an event must be **closed** before it can be **enriched**; closing is also what triggers alert evaluation on the backend.

The engine's own API (assistant, door verification, device health, camera and settings sync) is documented interactively by FastAPI at `/docs` once the service is running.

## 6. Requirements

- Python 3.10
- [Ollama](https://ollama.com) installed locally
- A running HomeGuard backend
- CPU is sufficient (developed and run on CPU on Windows); a GPU will improve throughput

## 7. Installation

```bash
git clone <repository-url> HomeGuardAI
cd HomeGuardAI

python -m venv venv
# Windows:
venv\Scripts\activate
# Linux/macOS:
source venv/bin/activate

pip install -r requirements.txt
```

Pull the language models:

```bash
ollama pull qwen2.5vl:7b
ollama pull gemma3:4b
```

Model weights:

- **YOLOv8**: `yolov8n.pt` is downloaded automatically by Ultralytics on first run if it is not already present at `YOLO_MODEL_PATH`.
- **InsightFace**: recognition models are downloaded automatically on first use.

## 8. Configuration

Create a `.env` file in the repository root. Do not commit it.

```dotenv
# Server
AI_SERVER_PORT=8001
DJANGO_API_URL=http://127.0.0.1:8000/api
API_SECRET_KEY=change-me          # must match the backend's AI-engine key
API_TIMEOUT=30

# Camera
CAMERA_SYNC_INTERVAL_SECONDS=30
EVENT_COOLDOWN_SECONDS=5
CAMERA_INDEX=0

# Motion
MOTION_MIN_AREA=2500

# YOLO
YOLO_MODEL_PATH=yolov8n.pt
YOLO_CONFIDENCE=0.45
YOLO_IOU=0.50

# Face recognition
FACE_MATCH_THRESHOLD=0.40

# Tracking
TRACK_BUFFER=30
TRACK_MATCH_THRESHOLD=0.80

# Recording
PRE_EVENT_SECONDS=5
POST_EVENT_SECONDS=5
CLIP_SECONDS=10

# Vision-language model
VLM_MODEL=qwen2.5vl:7b

# Cloudinary (clips and thumbnails)
CLOUDINARY_CLOUD_NAME=
CLOUDINARY_API_KEY=
CLOUDINARY_API_SECRET=
CLOUDINARY_FOLDER=
```

| Group | Variables | Effect |
|---|---|---|
| Server | `AI_SERVER_PORT`, `DJANGO_API_URL`, `API_SECRET_KEY`, `API_TIMEOUT` | Service port, backend address, shared-secret authentication, request timeout (seconds) |
| Camera | `CAMERA_SYNC_INTERVAL_SECONDS`, `EVENT_COOLDOWN_SECONDS`, `CAMERA_INDEX` | How often cameras are re-synced from the backend, minimum gap between events, default camera index |
| Motion | `MOTION_MIN_AREA` | Minimum changed area (pixels) to pass the motion gate |
| Detection | `YOLO_MODEL_PATH`, `YOLO_CONFIDENCE`, `YOLO_IOU` | Model file, confidence threshold, NMS overlap threshold |
| Recognition | `FACE_MATCH_THRESHOLD` | Cosine-similarity threshold for classifying a face as known |
| Tracking | `TRACK_BUFFER`, `TRACK_MATCH_THRESHOLD` | Frames a lost track is kept alive, association threshold |
| Recording | `PRE_EVENT_SECONDS`, `POST_EVENT_SECONDS`, `CLIP_SECONDS` | Clip buffer lengths and total clip duration |
| Language model | `VLM_MODEL` | Ollama model used for event summaries |
| Media | `CLOUDINARY_*` | Cloud media storage credentials |

## 9. Running

Start the HomeGuard backend first, then:

```bash
uvicorn app.main:app --reload --host 0.0.0.0 --port 8001
```

Interactive API documentation: `http://localhost:8001/docs`

Cameras are phone cameras whose stream URL is registered in the backend. The engine discovers them automatically at the configured sync interval.

## 11. Security and Privacy

- All backend calls carry a shared-secret credential; the engine has no user accounts.
- Face matching never crosses household boundaries.
- The engine stores nothing persistently: biometric data lives only in the backend, and media is uploaded then discarded locally.
- Language models run locally, so footage and summaries are not sent to third-party AI services.

## 12. Limitations

- Accuracy depends on lighting and on the distance between the person and the phone camera.
- Only pre-trained models are used; no custom training was performed.
- Throughput depends on host hardware and is not guaranteed for large numbers of simultaneous cameras.
- The smart-lock behaviour exercised through this service is a software simulation, not a physical lock.
